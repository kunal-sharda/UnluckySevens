# Messages Host Responsive Adaptation

## Purpose and Outcome

Make the existing Messages surfaces respond correctly to the actual host bounds supplied by iPhone and iPadOS, including the distinct widths observed when entering from the app drawer and from a transcript bubble. The system-owned host frame may differ; product content must fill, reflow, and remain legible without treating device identity as a layout input.

## Execution Settings

- Validation profile: `standard`
- Delivery posture: `checkpointed`
- Rationale: the host-size behavior is externally controlled and the responsive visual result requires real-iPad judgment before broader production cleanup.

## Context and Boundaries

- Apple owns the Messages extension frame. `requestPresentationStyle(.expanded)` requests a style, not an exact width.
- Layout resolves from live container width and height, never device model or `UIScreen.main`.
- This pass adapts the existing Lobby, UX Lab chrome, Start, and approved Turn compositions. It does not redesign legacy product surfaces.
- SpriteKit remains the board owner; container changes must not remount the live board.
- Existing dirty worktree changes are preserved.

## Milestones / Plan of Work

1. Add a pure host-layout profile covering narrow, narrow-short, standard, wide-short, and wide containers.
2. Make UX Lab quick navigation collapse into menus before labels wrap or cover product content; tuck settled legacy visual comparisons behind a clearly labeled menu.
3. Render the board/ocean as one canonical-aspect viewport. Fit it with one uniform scale derived from the live board region; never stretch either axis independently. Temporary Players, Games, Trade, Build, and forced-flow surfaces must not change that fitted viewport.
4. Add focused resolver tests for representative small/standard/large iPhones and both observed iPad host shapes, including canonical board-aspect and uniform-fit assertions; correct UI assertions to use the extension-local frame rather than the outer Messages window.
5. Capture exactly three representative iPad states (normal turn, Players, and Trade composer), inspect them, and stop for user review before the broader catalog rerun.
6. Remove tutorial-callout truncation and the trade-only color/style fork exposed by the rejected checkpoint; recapture Setup, Build, and Trade on iPad.
7. Verify the same Setup, Build, and Trade states independently in an iPhone Messages host using the exact same fresh build. The phone board and rail scale must not regress.
8. Treat the user's PDF review as a failed phone checkpoint: replace the tall/narrow cards with the compact-host treatment, add an explicit card-size assertion, and rerun all 16 lessons on both iPad and iPhone before presenting new proof.

### Discoveries

- The DEBUG quick-state row assumes phone-like horizontal room and wraps each label vertically in the narrower iPad transcript host.
- The physical layout currently clamps zone heights to phone-oriented ranges and has no wide-container proof.
- Apple continues to own the outer Messages panel width. The implementation scales physical objects and their reserved zones, not the entire SwiftUI root or the system host.
- The current `< 560` width rule sends both phone portrait and the shorter iPad Messages canvas through the same `.narrow` profile. Fixed vertical zones then consume the board's space.
- The gameplay UI test compares Game Information with the full Messages window midpoint. That happens to approximate the extension frame on iPhone but is not a valid iPad host-local centering assertion.
- Tutorial callouts use fixed 174x68 and 154x46 frames plus two- or three-line limits. Trade targets also select a separate dark treatment, which explains both user-reported truncation and the unexpected color change.
- A focused `test-without-building` run can refresh the test runner while Messages continues rendering a stale installed extension. The first correction capture reproduced the old style until the exact newly built `UnluckySevensApp.app` was installed and Messages was terminated. The canonical catalog runner already performs this install/restart/hash discipline; ad-hoc focused runs must do the same.
- The first stable-host iPhone run exposed an evidence-model error: SwiftUI's containing `uls.tabletop.board` accessibility union includes wrapper geometry and is not the rendered ocean viewport. The nested `uls.tabletop.boardHost` is the actual `SKView`; it passed the canonical ratio and the original-resolution screenshot showed an unstretched ocean. The reusable contract now measures aspect, centering, containment, and ordering against that mounted host rather than weakening the tolerance or changing correct product geometry.
- The first bounded retry passed the corrected board contract and reached the Players frame, then failed because XCTest reported the newly reacquired Trade element as non-hittable for four seconds after the overlay disappeared. This is the already-documented Messages stale-hit-target boundary, not a rendered product defect. The final allowed retry preserves the existence check, reacquires Trade through the shared resolver, taps its current frame, and judges success only by the destination Trade surface.
- Tutorial Trade then reproduced the same non-hittable state twice on a visibly unobscured 340x44 lobby Tutorial row. The new full-canvas DEBUG accessibility evidence element was layered after product content; although SwiftUI hit testing was disabled, XCTest treated it as accessibility occlusion.
