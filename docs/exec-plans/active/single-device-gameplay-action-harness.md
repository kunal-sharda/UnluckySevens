# Single-Device Gameplay Action Harness

## Purpose and Outcome

Add a repeatable iPhone 17 Messages-extension lane that seeds deterministic canonical states, operates real player-facing controls, and proves the resulting canonical state changed as expected. The expanded single-device scope covers every deterministic local gameplay mutation supported before the later real-device multiplayer matrix.

## Execution Settings

- Validation profile: `standard`
- Delivery posture: `direct`
- Rationale: The requested harness is meaningful test infrastructure with settled behavior and no product redesign or protocol change.

## Context and Boundaries

- [QA](../../quality/qa.md) owns simulator lifecycle, retry limits, and evidence rules. [First Friends TestFlight Release](first-friends-testflight-release.md) continues to own multi-device races, transport convergence, complete-match proof, and TestFlight.
- The lane runs first on iPhone 17, one test journey per XCTest process, after shutdown-all, target-only boot, uninstall, fresh install, Messages restart, and built/installed extension hash comparison.
- DEBUG fixtures may establish the initial canonical state and expose secrecy-safe diagnostics. The action under test must use the same player-facing control and production action publisher used outside DEBUG.
- No gameplay rules, protocol fields, approved UI/copy, typography, board art, or production release behavior changes.

## Milestones / Plan of Work

1. Expose a compact DEBUG-only canonical-state diagnostic containing revision, phase, turn step, active player, state hash, visible local hand, trade/discard/robber summaries, and last status.
2. Preserve the first seven isolated journeys: roll, discard, end turn, maritime trade, player trade offer, player trade acceptance, and development-card purchase.
3. Extend the same catalog with real board-target journeys for setup settlement/road, normal road/settlement/city construction, robber move/victim selection, and all playable development-card kinds: Knight, Monopoly, Year of Plenty, and Road Building. Victory Point remains passive rather than a playable action.
4. Expose DEBUG-only normalized live legal-target coordinates on the stable board-host diagnostic, but make XCTest tap the real SpriteKit surface twice where confirmation is required. Direct DEBUG action mutation is prohibited.
5. Add a cold-lifecycle catalog runner that records build/install hashes and per-journey xcresults, then execute and inspect the contracted iPhone lane.
6. Promote the durable command and limitations into QA; leave only multi-device concurrency, transport convergence, full-match proof, and physical-device entry proof in the release plan.
7. Add a bounded guardrail catalog covering production cancellation surfaces, trade decline, unavailable actions, illegal-placement exclusion, discard/robber/trade/Dev Card rule branches, and canonical no-mutation assertions where the player backs out or the engine rejects an action.
8. Add a bounded recovery catalog covering interrupted transient UI, extension close/reopen, canonical-state restoration, stable board/layout identity, and existing archive/restore and resignation recovery journeys on one iPhone.
9. Run the deterministic complete-match eval suite from lobby/setup through a canonical victory, then pair it with a production-wired victory/game-over UI journey without claiming that DEBUG fixture selection itself is gameplay transport proof.
10. Rerun the complete current iPhone visual catalog after the behavioral lanes pass.
11. Produce four ignored local review videos with rasterized headings: Guardrails and Cancellations, Rule Branches and Recovery, Complete Match, and Current UI Catalog. Trim harness launch/setup time, preserve the actual action/result interval, and inspect decoded frames from every final export.
12. Replace hand-authored gameplay fixture piece maps with reducer-derived legal positions, guard every board fixture against disconnected roads or floating buildings, and produce a current-source headed movie from the real XCUITest touch recordings for all 17 actions. A screenshot-derived movie does not satisfy this deliverable.
13. Make Messages navigation state-driven rather than tap-count-driven, retain failure diagnostics automatically, and replace the initial-plus-two circuit breaker with a diagnostic-first ceiling of ten focused reruns.
